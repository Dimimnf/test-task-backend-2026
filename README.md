# Синхронизация CRM с PostgreSQL

Точка входа полной синхронизации: `collect_leads_customers(is_full=True)`.
Celery, брокер, боевой CRM API и HTTP-сервер Flask для запуска и тестов не нужны.

## Что было дорого

Исходная реализация выполняла поиск, запись и `commit` для каждой сущности. На 20 000 покупателей и 50 000 сделок это приводит к десяткам тысяч отдельных транзакций и сетевых round-trip к PostgreSQL. Cleanup также передавал большой набор ID как отдельные SQL-параметры, что плохо масштабируется и может превысить лимит параметров PostgreSQL.

## Что изменено

- CRM-выгрузка остаётся потоковой: клиент отдаёт генератор со страницами до 250 записей, без загрузки всего набора в память.
- `SyncBatchWriter` накапливает до 500 строк и связей, выполняет PostgreSQL `INSERT .. ON CONFLICT DO UPDATE` для CRM-сущностей и `ON CONFLICT DO NOTHING` для связей.
- `collect_customers` и `collect_leads` сведены к единому batch-конвейеру; построчный fallback без `SyncBatchWriter` удалён.
- ID новых агрегатов резервируются блоками из PostgreSQL sequence, без построчного `INSERT` ради получения ID.
- Merge агрегатов использует set-based `UPDATE` и перенос связей без промежуточных commit. Ещё не записанные строки и связи перенаправляются к целевому агрегату.
- Cleanup выполняется только после успешной фиксации всех пакетов. Все удаления входят в одну транзакцию; ID передаются одним PostgreSQL array bind.
- `BaseDAL.delete_not_in_ids` защищён от пустого набора ID: при отсутствии `keep_ids` удаление не выполняется.
- CRM-клиент `amocrm_get` строит `Customer`/`Lead` напрямую из JSON-ответа, без внешних сериализационных схем.
- Добавлен baseline `migrations/001_initial_schema.sql` для новой PostgreSQL-БД. Он идемпотентен, но не предназначен для преобразования неизвестной существующей схемы.

## Компромиссы и ограничения

- При сбое откатывается текущий незавершённый пакет. Ранее зафиксированные пакеты остаются в БД, а cleanup не запускается. Это осознанная альтернатива одной длинной транзакции на весь проход; следующий полный запуск приведёт данные к актуальному состоянию.
- Сопоставление по CRM ID и логину сохранено буквально по правилам задания, но lookup выполняется prefetch-окнами до 250 записей: ID и логины загружаются пакетными запросами, а при commit/merge кэш оставшейся части окна обновляется.
- `SyncState` хранит ID встреченных сущностей до конца полного прохода, поскольку они нужны cleanup. Для 20 000 покупателей, 50 000 сделок и до 70 000 агрегатов это около 10,3 MiB; буфер из 500 синтетических JSON-записей добавляет примерно 0,6 MiB. Оценка не включает текущую CRM-страницу, SQLAlchemy и объекты вложенных contacts/companies.
- Пакетная запись сокращает 70 000 основных сущностей минимум до порядка 140 batch-циклов вместо десятков тысяч одиночных commit. Точное число операций выше при новых агрегатах и связях. Для каждой страницы matching выполняет пакетные SELECT по ID, группировку логинов и загрузку найденных агрегатов; число запросов теперь пропорционально числу окон, а не числу сущностей.

## Проверка

Интеграционные тесты используют PostgreSQL, а не SQLite, так как проверяют PostgreSQL upsert, JSONB и array bind. Проверены batch-upsert, JSONB, связи без дубликатов, merge с приоритетом сделки, неоднозначные логины, маркер удаления, cleanup, rollback и миграция.

```powershell
pip install -r requirements.txt

docker run --rm -d --name test-task-postgres `
  -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=test `
  -p 55432:5432 postgres:16

do {
  Start-Sleep -Seconds 1
  docker exec test-task-postgres pg_isready -U test -d test
} until ($LASTEXITCODE -eq 0)

$env:TEST_DATABASE_URL = "postgresql+psycopg://test:test@127.0.0.1:55432/test"
python -m unittest discover -s tests -v
python -m tests.profile_sync_memory

# Проверка baseline-миграции на отдельной чистой БД
docker exec test-task-postgres createdb -U test migration_test
docker cp migrations/001_initial_schema.sql test-task-postgres:/tmp/001_initial_schema.sql
docker exec test-task-postgres psql -U test -d migration_test -v ON_ERROR_STOP=1 -f /tmp/001_initial_schema.sql
$env:TEST_DATABASE_URL = "postgresql+psycopg://test:test@127.0.0.1:55432/migration_test"
$env:TEST_DATABASE_USE_MIGRATION = "1"
python -m unittest discover -s tests -v

docker stop test-task-postgres
```

Без `TEST_DATABASE_URL` PostgreSQL-интеграционные тесты пропускаются. Flask используется исключительно как контейнер конфигурации `Flask-SQLAlchemy` и application context, без запуска HTTP-сервера.

## Пакетное сопоставление

Для каждого окна CRM до 250 покупателей или сделок создаётся ограниченный `MatchCache`, поэтому сопоставление выполняется пакетно:

- записи загружаются по CRM ID одним `IN`-запросом;
- связанные агрегаты загружаются вместе через `joinedload`;
- поиск по логинам выполняется группировкой `GROUP BY login`;
- неоднозначным считается логин, связанный с несколькими различными агрегатами, как и требовалось исходной бизнес-логикой;
- после commit или merge кэш оставшейся части окна перечитывается, чтобы не использовать устаревшие соответствия.

Кэш ограничен текущим окном и не хранит всю выгрузку. Поэтому количество matching-запросов зависит от числа окон, а не от количества отдельных CRM-сущностей.

## Почему несколько таблиц

Агрегат покупателя хранится отдельно от CRM-покупателя, сделки, контакта и компании. Это разделение нужно потому, что у одного клиента могут быть одновременно покупатель и несколько сделок, а контакты и компании могут быть общими для разных агрегатов. Связи вынесены в отдельные таблицы с составным первичным ключом.

Такое хранение позволяет:

- не дублировать общие контакты и компании;
- отдельно обновлять покупателя, сделку и вложенные сущности по CRM ID;
- выполнять merge агрегатов переносом связей, не переписывая все JSON-данные;
- удалять устаревшие сущности каскадно после успешного полного прохода;
- иметь индексы по CRM ID, логину, названию и внешним ключам.

Единая таблица была бы проще на старте, но привела бы к смешению разных типов сущностей, дублированию данных и более сложному поиску/обновлению. При выбранной схеме ночная синхронизация работает с отдельными таблицами, а логическая связь покупатель-сделка сохраняется через общий `abstract_customer_id`.

## Результаты тестирования

Добавлены unit- и PostgreSQL-интеграционные тесты. На временном PostgreSQL 16 успешно пройдено 20 тестов, включая:

- пакетный upsert и JSONB;
- один commit на пакет из 500 строк;
- rollback текущего пакета и отсутствие cleanup после ошибки;
- merge с переносом связей и ожидаемым приоритетом сделки;
- уникальное и неоднозначное сопоставление по логину;
- приоритет поиска по CRM ID;
- пропуск покупателя без логина и обработку маркера удаления;
- дедупликацию связей;
- cleanup с одним array bind для 65 536 ID;
- пакетный prefetch matching с шестью SELECT вместо построчных запросов в тестовом окне;
- применение baseline SQL-миграции и запуск тестов на созданной ею схеме.

Проверка памяти показала около 10,3 MiB для ID-наборов `SyncState` и около 0,6 MiB для буфера из 500 синтетических JSON-записей. Полный объём CRM не запускался, так как боевого API в репозитории нет.
